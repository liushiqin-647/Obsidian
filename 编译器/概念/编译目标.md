> [!info] 核心一句话
> **编译目标（target）** = 编译器把源码翻译成的"机器语言环境"，用 **target triple** 描述（`架构-厂商-操作系统-ABI`）。选不同的 target，就是给同一份源码生成不同平台的机器码。

## Target Triple 的组成

```
x86_64 - unknown - linux - gnu
 架构      厂商       OS     ABI
```

| 字段              | 作用                 | 常见取值                                          |
| --------------- | ------------------ | --------------------------------------------- |
| **架构**（arch）    | 指令集、寄存器、寻址模式       | `x86_64`、`aarch64`、`riscv64`、`armv7`、`wasm32` |
| **厂商**（vendor）  | 标识平台变体             | `unknown`、`pc`、`apple`、`linux`                |
| **操作系统**（OS）    | 决定系统调用、动态链接、进程模型   | `linux`、`darwin`、`windows`、`none`（裸机）         |
| **ABI/环境**（env） | 调用约定、结构体布局、libc 选择 | `gnu`（glibc）、`musl`、`msvc`、`eabi`、`eabihf`    |

典型例子：

- `x86_64-unknown-linux-gnu`：最常见的 Linux x86-64（glibc 动态链接）
- `x86_64-unknown-linux-musl`：Linux + musl，**静态链接友好**
- `aarch64-apple-darwin`：Apple Silicon Mac
- `x86_64-pc-windows-msvc`：Windows + MSVC ABI
- `riscv32imac-unknown-none-elf`：RISC-V 裸机嵌入式（无 OS、无标准库）

### 厂商字段到底代表什么

厂商 = "谁家的平台/品牌"，**不是操作系统**（OS 是第三段）。历史遗留字段，主要**消歧**：

- `unknown`：通用场景默认，绝大多数 Linux 目标用它
- `pc`：IBM-PC 兼容机，Windows x86 目标的惯例
- `apple`：苹果平台（硬性要求，填错选不到正确 target）

华为机器的实际写法（并没有 `huawei` 这个厂商）：

- **鲲鹏 / 麒麟**（标准 ARM 架构）→ `aarch64-unknown-linux-gnu`，厂商依然是 `unknown`
- **鸿蒙 / OpenHarmony** → OS 段是 `ohos`：`aarch64-unknown-linux-ohos`、`x86_64-unknown-linux-ohos`（LLVM/Rust 官方支持，Linux 内核 + musl 用户态）
- **昇腾**（DaVinci 自研架构）→ 不走标准 target triple，用华为自家 CANN 工具链
- 鲲鹏的"华为味"体现在 **CPU 调优**：GCC 的 `-mcpu=tsv110`（TSV110 是鲲鹏 920 的内核代号）

厂商段只在"架构+系统组合有歧义"时才有存在感，所以标准 ARM 芯片的厂商都是 `unknown`。

## Target 决定了什么

- **指令集**：能用哪些指令（SSE/AVX/NEON 等，由 target 隐含的默认 + 特性开关决定）
- **数据模型**：指针宽度（32/64 位）、`long` 大小、端序（大/小端）
- **调用约定与 ABI**：参数怎么传、结构体怎么排布、符号名怎么修饰（C++ 的 Itanium/MSVC mangling）
- **标准库与运行时**：glibc vs musl vs MSVC CRT；`std` vs `no_std`
- **文件格式**：ELF（Linux）、Mach-O（macOS）、PE/COFF（Windows）、WASM
- **默认链接器与汇编器**：以及动态链接器路径（`/lib64/ld-linux-x86-64.so.2`）

## 编译器里怎么指定

| 工具 | 方式 |
|---|---|
| clang | `clang --target=aarch64-unknown-linux-gnu foo.c` |
| GCC | configure 时 `--target=...`；运行时用 `-m32`、`-march=` 等近似 |
| rustc | `rustc --target aarch64-unknown-linux-gnu`；`rustup target add` 装目标 |
| rustc 自定义 | `-Z build-std` + target JSON（嵌入式裸机常用） |

- **默认 target** = 编译器的"本机"（host triple），交叉编译时才显式指定
- **目标特性（target features）**：在 target 基础上细调，如 GCC `-march=native`、rustc `-C target-cpu=native -C target-feature=+avx2`

## 交叉编译（target ≠ host）

同一份源码，目标平台和当前机器不同 → 需要**交叉工具链**：

```
源码 ──clang --target=aarch64-linux-gnu──> aarch64 机器码
        ↑
  需要: 交叉 libc（sysroot）、交叉链接器、目标平台的标准库
```

- Rust 交叉编译最省事：`rustup target add x86_64-unknown-linux-musl` + 装个交叉链接器即可
- clang 天然是交叉编译器（一个 clang 认识所有 target），但缺**目标平台的库和 sysroot**——所以"clang 能编但链不上"是常见问题
- 链接的每个库都必须与 target 的 ABI 匹配（混用 glibc/musl、gnu/msvc 产物会链接失败或运行崩溃）

## 常见坑

> [!warning] 注意
> - **ABI 不匹配**是最大的坑：`-m32` 编译的库和 64 位主程序混链，符号对不上
> - **no_std / 裸机 target**（`*-none-*`）：没有操作系统，也没有 Rust/C 标准库，只能自己提供内存管理和入口
> - **target 与二进制分发**：容器里编的产物带容器 glibc，分发要选 `musl` 或静态链接
> - target 特性开过头（`-C target-feature=+avx512`）编出的二进制在旧 CPU 上会 **illegal instruction**

## 一句话总结

编译目标是编译器"写给谁看"的完整描述：**架构定指令、OS 定系统接口、ABI 定二进制兼容**；普通开发用默认 target，交叉编译/嵌入式/分发场景才需要显式指定并准备对应的库和链接器。
