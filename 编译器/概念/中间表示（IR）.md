# 中间表示（IR）

IR（Intermediate Representation，中间表示）是编译器内部的"中介语言"：既不是人类写的源码，也不是 CPU 能直接执行的机器码，介于两者之间——抽象到足够通用，具体到足够翻译成机器指令。

## 为什么需要 IR

用翻译类比最直观：要把中文翻译成法语、德语、西班牙语。

- **直接翻译**：同时精通中文和每种目标语言的人直接翻。想支持新语言就得再找人。
- **借助中介语言**：先把中文翻成英语，再由懂英语和法语的人把英语翻成法语。想翻德语？同一版英语再翻一遍就行。

编译器同理：

- **前端**：把各种语言（C、C++、Rust、Go……）翻译成 IR（"中介语言"）
- **后端**：把 IR 翻译成各架构（x86、ARM、RISC-V……）的机器码

这样"N 种语言 × M 种架构"就不需要 N×M 个编译器，只需要 N 个前端 + M 个后端。

## IR 不是统一格式

"IR" 是概念，不是世界通用的标准。每个编译器体系都有自己的 IR：

| 编译器/运行时 | IR 格式 | 说明 |
|---|---|---|
| **LLVM**（clang、rustc 等） | LLVM IR | 各语言最终收束到同一种 LLVM IR |
| **GCC** | GIMPLE、RTL | 先降到 GIMPLE，再降到更贴近机器的 RTL |
| **JVM**（HotSpot） | Java 字节码 | Java、Kotlin、Scala 等都编译成同一种字节码 |
| **.NET CLR** | CIL | C#、F#、VB.NET 最终都翻译成 CIL |
| **WebAssembly** | WASM 字节码 | C、Rust、Go 等都能编译到同一种 WASM |

关键区分：

- **同一工具链内**：不管什么语言，最终都翻译成该工具链约定的那一种 IR
- **跨工具链**：LLVM IR、GIMPLE、Java 字节码、CIL 格式完全不同，互不兼容
- **IR 有层次**：有的偏抽象（贴近高级语言形态），有的已经很接近机器码；同一编译器内部甚至可能用多种不同层级的 IR

## 前端、中端、后端与 IR

```
源码 → [前端] → IR → [中端优化] → IR' → [后端] → 机器码
```

- **前端**：理解并翻译语言。词法、语法、语义分析只是手段，**最终目的是生成 IR**；除此之外还包含预处理、脱糖、IR 生成等工作（见 [[前端 vs 后端]]）
- **中端**：在 IR 上做机器无关优化（内联、常量传播、循环优化等）。语言无关、目标无关，新语言新架构都复用这一套
- **后端**：把 IR 翻译成具体目标的机器码，负责指令选择、指令调度、寄存器分配、代码发射（见 [[编译目标]]、[[调度模型]]）

前端产出什么 IR、后端认什么 IR，由各工具链自己约定。以 rustc 为例，它有自己的 IR 层次（AST → HIR → MIR），MIR 之后才交给 codegen 后端，详见 [[rustc codegen 后端选择]]。

## 核心要点

- **IR 是中介语言**：把 N×M 的编译器矩阵简化为 N 个前端 + M 个后端
- **IR 格式不统一**：每个编译器体系自己定义，LLVM IR / GIMPLE / Java 字节码之间互不兼容
- **IR 是前后端的"合同"**：前端按规范生成 IR，后端按规范消费 IR，两边互不了解对方细节
- **IR 是优化发生的地方**：中端所有机器无关优化都在 IR 上进行，这也是 PGO、LTO 等优化的基础（见 [[PGO]]、[[LTO]]）
