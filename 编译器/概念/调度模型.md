> [!info] 核心一句话
> 编译器的**指令调度** = 在不改变程序语义的前提下**重排指令顺序**，让处理器流水线少停顿、功能单元不冲突。编译器里的"调度模型"则是描述目标 CPU 的**指令延迟、资源占用**等信息，供调度器做决策。

## 为什么需要调度

处理器流水线把一条指令拆成取指→译码→执行→访存→写回多个阶段，**有依赖的指令之间存在延迟**：

```
mov eax, [mem]    ← 访存指令，延迟 3~4 周期
add eax, 1        ← 依赖 eax，必须等它读回来 → 流水线停顿（stall）
```

调度就是插入/重排无关指令来填平这段等待。收益取决于硬件：

| 硬件类型 | 行为 | 编译器调度的意义 |
|---|---|---|
| **顺序执行（in-order）** | 停顿就白白浪费周期 | 收益巨大，必须靠编译器隐藏延迟 |
| **乱序执行（out-of-order）** | 硬件靠重排序缓冲（ROB）自己重排 | 收益小但仍有用：减轻硬件窗口压力、减小代码体积 |
| **VLIW / 显式并行** | 硬件完全听话，不做动态调度 | 调度就是编译器的核心职责，排不好就直接错 |

## 依赖关系类型（调度能做什么的前提）

| 类型 | 名称 | 能否消除 |
|---|---|---|
| RAW（读后写） | 真依赖 / 流动依赖 | **不能**，必须等待，只能穿插无关指令隐藏 |
| WAR（写后读） | 反依赖 | 可消除（寄存器重命名 / 分配时换寄存器） |
| WAW（写后写） | 输出依赖 | 可消除（同上） |
| 控制依赖 | 分支约束 | 默认不能跨越，除非做投机调度 |

## 调度模型分类

### 局部调度（基本块内）

对单个基本块建**数据依赖图（DAG）**：节点 = 指令，边 = 依赖关系 + 延迟。然后用**列表调度（List Scheduling）**：

1. 计算每条指令的优先级（关键路径长度优先）
2. 维护**就绪队列**：所有依赖已满足、且资源可用的指令
3. 每周期从就绪队列中选最高优先级指令发射，更新队列

```
// 优化前：顺序发射，访存延迟暴露
t1 = load [p]      // 延迟 3
t3 = t1 + 1        // ← 要等 3 周期，流水线冒泡
t2 = load [q]
t4 = t2 + 1
r  = t3 * t4

// 调度后：两个无关 load 先发，等待期互相覆盖
t1 = load [p]
t2 = load [q]      // 趁 t1 还在路上，先发无关的
t3 = t1 + 1
t4 = t2 + 1
r  = t3 * t4
```

### 全局调度（跨基本块）

单基本块通常只有 5~10 条指令，可调度空间太小，于是：

- **Trace Scheduling**：挑出最可能执行的路径（trace）当作一个大块来调度，调度跨越分支；跨出 trace 的旁路路径用**补偿代码（bookkeeping code）**修复语义
- **Superblock / Region scheduling**：基于区域合并基本块再调度

### 循环调度（收益最集中）

**软件流水（Software Pipelining）**：让相邻迭代的重叠执行——第 i+1 次迭代的取数和第 i 次迭代的计算同时进行：

```
// 传统展开：迭代之间完全串行
load  a[0] → 计算 → 存  |  load a[1] → 计算 → 存  | ...

// 软件流水：三个阶段重叠
prologue: load a[0]                  ← 预热
steady:   load a[i+1] ∥ 计算 a[i]    ← 每周期同时干两件事
epilogue:                   计算 a[n-1] 收尾
```

**模调度（Modulo Scheduling）**是其形式化版本：算出一个**迭代启动间隔（II, Initiation Interval）**，所有迭代按模数表排布，以 II 个周期为周期发射。VLIW/DSP 编译器（如 TI、Itanium 系）的标准武器。

### VLIW 与超标量

- **VLIW**（Itanium/IA-64、DSP）：一条指令字里打包多个操作，硬件照单执行。编译器就是唯一的调度器，必须同时考虑依赖和资源（发射端口、功能单元数量）
- **超标量**：硬件动态调度（Tomasulo 算法），编译器调度是"辅助性的"，主要减少硬件窗口压力

## LLVM 的调度模型（SchedModel）——具体实现

现代编译器里"调度模型"通常特指 LLVM 用 **TableGen** 描述目标 CPU 的那套定义，调度器读它做决策：

```tablegen
// X86/X86Schedule.td 里的典型写法
def : ProcResource<[Port0, Port1, Port5]>;   // 定义发射端口

// 定义某指令的延迟和资源占用
def : WriteRes<WriteIMul, [Port1]> {         // 整数乘法
  let Latency = 3;                            // 延迟 3 周期
  let ResourceCycles = [1];
}

def : ReadAdvance<ReadIMul, 2>;               // 乘法结果的部分位提前可用
```

模型要素：

- **ProcResource**：发射端口、功能单元（ALU/FPU/LoadStore）
- **WriteRes / Latency**：每条指令的产生延迟和资源占用周期
- **ReadAdvance**：提前可用性（如乘法高位/低位不同时可用）
- **Itinerary**：老式逐级流水线描述（`InstrItineraryData`）
- **调度器策略**：LLVM 的 `MachineScheduler` 支持压力跟踪、寄存器压力启发式（避免调度过度导致溢出）

## 一个完整的列表调度例子

假设单发射、load 延迟 3 周期、ALU 延迟 1 周期。指令：`A=load`、`B=load`、`C=A+1`、`D=B+1`、`E=C*D`：

| 周期 | 顺序执行 | 列表调度 |
|---|---|---|
| 1 | A | A |
| 2 | 停顿 | B |
| 3 | 停顿 | 停顿（等 A） |
| 4 | B | C |
| 5 | 停顿 | 停顿（等 B） |
| 6 | C | D |
| 7 | 停顿 | E |
| 8 | D | |
| 9 | 停顿 | |
| 10 | E | |

列表调度把 10 个周期压到 7 个。真实代码基本块里几百条指令，收益更明显。

## 用 llvm-mca 观察调度

LLVM 自带 **Machine Code Analyzer（llvm-mca）**，模拟指定 CPU 的流水线并输出报告：

```bash
clang -O2 -S -emit-llvm demo.c -o - | llc -mcpu=skylake - | llvm-mca -mcpu=skylake
```

输出能看：每周期发射情况、资源压力、瓶颈在哪类指令。写热循环时对比优化前后非常实用。

## 调度 vs 寄存器分配：次序难题

经典"鸡生蛋"问题：

- **先调度后分配**：调度假设寄存器无限，分配时可能引入大量新的伪依赖（反依赖/输出依赖），把调度效果毁掉
- **先分配后调度**：分配引入的依赖严重压缩调度自由度
- 实际做法：分阶段多次迭代（调度 → 分配 → 重调度），或用 SSA 形式减少伪依赖

## 一句话总结

调度模型的本质是**"用编译期知识换运行期性能"**：依赖图给出约束，延迟/资源表给出成本，列表调度、trace 调度、软件流水把无关指令填进等待周期里；LLVM 的 SchedModel 则是这套思想的工程化描述文件。
