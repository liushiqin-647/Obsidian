# 沙箱与容器、以及沙箱的隔离性要求

## 1. 概念澄清

- **沙箱**是"目的/大类"：任何受限、隔离的执行环境。
- **容器**是其中一种具体实现（namespace + cgroup + seccomp）。
- 所以**容器本身也是一种沙箱**；要对比的是 **"VM 类沙箱" vs "容器"**。

沙箱的实现类型：

| 类型 | 隔离方式 | 例子 |
|---|---|---|
| 硬件虚拟化 | 独立内核 | Firecracker、QEMU/KVM、Kata |
| 用户态内核 | 拦截系统调用模拟内核 | gVisor |
| 系统调用过滤 | 限制 syscall | seccomp |
| 权限/视图 | 降权、命名空间 | chroot、namespaces |
| 语言/运行时 | 解释器隔离 | WebAssembly、JVM、浏览器沙箱 |

## 2. 沙箱为什么对隔离性有要求

沙箱的本质是在**信任边界**一侧跑不可信代码：

```
可信侧（宿主/其它租户/数据） │ 信任边界 │ 不可信侧（沙箱内代码）
```

五个根本原因：
1. **运行不可信代码**（第三方/用户/插件/AI agent 动作）；
2. **控制爆炸半径**（被攻破也局限在沙箱内）；
3. **多租户互不可见**；
4. **最小权限**（只给必需访问）；
5. **资源约束**（防 DoS）。

**强度由威胁模型决定**：防误操作 → 弱隔离够；跑第三方 → 中；云多租户/完全不可信 → 强隔离（独立内核 VM）。容器共享内核，一旦内核漏洞就可能逃逸，故"完全不可信"场景常常不够。

隔离需覆盖的维度：进程/内核、文件系统、网络、设备、资源、侧信道。

## 3. VM 类沙箱 vs 容器

| 维度 | VM 类沙箱 | 容器 |
|---|---|---|
| 隔离机制 | 虚拟化（KVM） | namespace+cgroup+seccomp |
| 内核 | 每个实例独立 | 共享宿主内核 |
| 隔离强度 | 强（漏洞仅影响单实例） | 较弱（可逃逸） |
| 启动开销 | 较重（microVM 已到百毫秒级） | 轻（毫秒级） |
| 资源开销 / 密度 | 有内核开销 / 较低 | 很轻 / 高 |
| 快照/迁移 | 原生整机快照 | 难（需 CRIU） |
| 兼容性 | 像真机，可特权/嵌套虚拟化 | 跑 Linux 应用，受内核限制 |
| 典型实现 | Firecracker、Kata、Cloud Hypervisor | Docker/runc、containerd |

**本质**：容器 = 共享内核（轻快、隔离弱）；VM 沙箱 = 独立内核（重些、隔离强）。

## 4. AgentENV 为什么选微VM

Kimi K3 技术报告 §5.3.2 的三个理由：
1. **agent 会激进探索甚至 reward hacking** → 需要强隔离；
2. **复杂任务要接近真机**（挂盘、跑容器、起 VM）；
3. **需要整机快照/快速恢复**（推理等待占生命周期 98%）。

> Kimi K3 同时使用 container-based、GPU sandbox、microVM 多种 runtime；微VM 不是取代容器，而是"强隔离+真机环境+快照"场景的更优选择。

## 5. 结论

**容器是共享内核的轻量沙箱；VM 沙箱是独立内核的强隔离方案。** 沙箱对隔离性的要求源于"要安全收留不可信的东西"，强度由威胁模型决定；AgentENV 因需要强隔离、真机环境与整机快照而选择 Firecracker microVM。
