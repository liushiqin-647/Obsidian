> AgentENV 沙箱指令派发链路详解：agent → AgentENV → Firecracker 沙箱。
> 所有结论以源码为依据（/home/liushiqin/AgentENV）。

## 第 0 章：先认识这些角色

| 角色 | 是什么 | 住在哪里 |
|---|---|---|
| **agent** | 调用方，比如 AI 编程助手。它通过 **E2B SDK**（一个客户端库）发请求 | 你自己的机器/程序里 |
| **AgentENV 服务器** | Rust 写的主服务进程，监听 **8000 端口**（`src/bin/server.rs` L86）。它既是"管理员"（创建/删除沙箱）也是"邮递员"（转发指令） | 一台 Linux 宿主机 |
| **Firecracker** | AWS 开源的微型虚拟机管理器。每创建一个沙箱 = 启动一个 Firecracker 进程 = 一台微型 Linux 虚拟机（VM） | 同一台宿主机上 |
| **envd** | 预先放在虚拟机里的"贴身管家"程序，监听 **49983 端口**。它在 VM 内部真正执行命令、读写文件 | **虚拟机内部** |
| **scheduler / gateway** | 可选的多机组件：gateway 是"前台接待"，scheduler 是"登记处"，记录每个沙箱在哪台机器上 | 多机部署时才存在 |

关键名词补充：

- **UDS**（Unix Domain Socket）：宿主机上的"内线电话"，是一个特殊文件，AgentENV 主进程通过它给 Firecracker 下管理命令。只在本机有效，外界摸不到。
- **netns**（网络命名空间）：Linux 的网络隔离技术。每个沙箱分到自己的"独立网段"，互相看不见。
- **token**（访问令牌）：一串随机字符，相当于沙箱的"钥匙"。创建时生成，之后每次执行命令都要出示。
- **gRPC / h2c / HTTP/1.1**：HTTP 上的通信协议。h2c = 不加密的 HTTP/2；gRPC 是远程调用框架。envd 同时支持，客户端优先试 h2c，不行退 HTTP/1.1。
- **DNAT/SNAT**：iptables 的地址改写规则，把发往"沙箱访问 IP"的流量改写成 VM 内部真实 IP。
- **runit / runsv**：VM 内的进程监督器，envd 崩溃了会自动拉起。
- **tools drive**：一块只读系统盘（OCI 镜像 `agentenv-tools` 打包），所有沙箱共用，里面装着 VM 启动脚本（init）和 envd 程序本身。

## 第 1 章：创建沙箱（agent 拿到"房卡和钥匙"）

**这是所有事情的前提。**

**1.1** agent 向 AgentENV 的 8000 端口发 HTTP 请求：

```
POST http://<服务器IP>:8000/sandboxes
Body: { "templateID": "python基础镜像", ... }
```

**1.2** 服务器开始"造房子"（这条路径走 Firecracker API）：

- 启动一个 Firecracker 进程
- 通过 **UDS** 告诉它：用多少 CPU/内存（`src/sandbox/firecracker/instance.rs` L289）、挂哪两块盘、配什么网络（L383），最后下 `InstanceStart` 开机指令（L445）
- 两块盘：**vda = tools drive**（只读系统盘，所有沙箱共用，里面装着启动脚本和 envd 程序）、**vdb = 用户镜像**（你的环境）

**1.3** VM 开机后，envd 自动上岗：

- 开机时内核参数里自动带 `init=/init`（`src/sandbox/firecracker/sandbox.rs` L1540）——意思是"用 tools drive 里的 init 脚本作为 1 号进程"
- init 脚本启动进程监督器 **runit**，runit 拉起 envd 并盯着它（崩了自动重启，见 `tests/integration/envd_supervisor.rs`）
- 宿主机上的 AgentENV 反复请求 `http://<沙箱IP>:49983/health` 探活，确认 envd 活着后，调它的 `/init` 接口把**本沙箱的 access token** 发给它（`src/sandbox/envd.rs` L158-205）。从此 envd 只认带这个 token 的请求

**1.4** 服务器回给 agent 一个"入住凭证"（`src/api/impls/sandbox.rs` L536-549）：

```json
{
  "sandboxID": "isbx_abc123",       ← 房号
  "envdAccessToken": "xxx",          ← 钥匙
  "domain": "sandboxes.example.com"  ← 小区名
}
```

**agent 就是这样知道沙箱 ID 的——是创建接口返回的。**

## 第 2 章：执行命令（以 `ls /tmp` 为例）

### 2.1 agent 发出请求

SDK 拼出一个 URL 再发请求。它有两种拼法，效果一样：

**方式 A（域名寻址，E2B SDK 默认）：**

```
POST https://49983-isbx_abc123.sandboxes.example.com/process.Process/Start
```

域名规则是 `{端口}-{沙箱ID}.{域名}`。DNS 把这个域名解析到 AgentENV 服务器，所以请求实际还是打到服务器的 8000 端口。

**方式 B（请求头寻址）：**

```
POST http://<服务器IP>:8000/process.Process/Start
Headers:
  e2b-sandbox-id: isbx_abc123
  e2b-sandbox-port: 49983
  x-access-token: <钥匙>
```

注意路径 `/process.Process/Start` 是 **envd 自己的接口路径**——AgentENV 看到这个路径就知道："这不是找我的，是要转给某个沙箱的"。

### 2.2 （多机场景）gateway 先接客

如果集群有好多台宿主机，请求先到 **gateway**（Go 写的接待台，`services/gateway/internal/server.go` L187）：

1. gateway 拿着沙箱 ID 问 scheduler："isbx_abc123 住哪台机器？"（`LookupNode`，L254）
2. 拿到机器地址后，把请求**原封不动转发**过去（L358-372）

单机部署时跳过这步。

### 2.3 AgentENV 主进程：验钥匙、查房号

请求到达对应机器，经过两层（`src/api/server.rs` L36-49）：

**第一层：鉴权**（`src/api/impls/auth.rs` L43-135）

- 检查 `x-access-token` 是不是这个沙箱创建时发的那把钥匙，不对就拒绝

**第二层：反向代理路由**（`src/api/proxy.rs`）

- 方式 A 的请求：从 Host 头 `49983-isbx_abc123....` 里拆出沙箱 ID 和端口（L333）
- 方式 B 的请求：直接读请求头（L86-92）
- 然后拿沙箱 ID 查**内存路由表**：`沙箱ID → 这个沙箱在宿主机上的访问 IP`（`src/orchestrator/service.rs` `proxy_lookup_for` L942）

查表结果有三种：

- **沙箱在跑** → 拿到 IP，继续转发
- **沙箱已暂停** → 先从磁盘快照把它唤醒，再重试转发
- **查无此箱** → 返回 404

### 2.4 流量穿过宿主机网络栈，进入虚拟机

拿到 IP 后，请求被发往 `http://<沙箱访问IP>:49983`。

这里有个"地址改写"环节：每个沙箱有自己独立的 netns（网络小天地），宿主机上的 iptables 规则会把发往"沙箱访问 IP"的流量改写成 VM 内部真实 IP（`src/sandbox/network/slot.rs` L534-577）。就像快递送到小区门口的代收点，代收点再转给具体住户。

**注意：这一步从头到尾是普通 TCP 网络，完全不碰 Firecracker 的 UDS 管理通道。**

### 2.5 VM 内部：envd 真正执行命令

请求到达 VM 内的 envd（49983 端口）。envd 校验 token 后：

1. 在 VM 里真正 fork 出 `ls /tmp` 进程
2. 收集它的 stdout、stderr、退出码
3. 以**流式响应**的形式逐步回传（命令边跑边吐输出）

回传沿原路返回：envd → iptables → AgentENV 主进程 → （gateway）→ SDK → agent。

**全程 Firecracker 都在沉睡，它根本不知道有命令被执行了。**

## 第 3 章：全景总结

```
agent (E2B SDK)
  │  POST {端口}-{沙箱ID}.{域名}/process.Process/Start   (或 8000端口+请求头)
  │  带着创建时拿到的 沙箱ID + access token
  ▼
[gateway] ──问 scheduler──▶ 路由到正确的宿主机（多机才有）
  ▼
AgentENV:8000 ── 鉴权(查钥匙) ── 反代(查房号→IP)
  ▼
iptables 地址改写 ──▶ VM 内 envd:49983 ──▶ 真正执行 ls /tmp
  ▼
输出沿原路流式返回
```

**两条互不交叉的通道：**

| | 控制面（管机器） | 数据面（用机器） |
|---|---|---|
| 干什么 | 创建、开机、暂停/恢复、拍快照、销毁 | 执行命令、传文件、交互终端、探活 |
| 走什么 | UDS → Firecracker API | TCP HTTP → 反向代理 → envd:49983 |
| 谁知道 | 只有 AgentENV 主进程 | agent（凭沙箱ID+token） |

**一句话：Firecracker 只管"造和拆虚拟机"，造好之后的一切使用都通过 HTTP 反代找 VM 里的 envd 管家办。**
